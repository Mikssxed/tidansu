# Tidansu — Security Review
**Date:** 2026-08-11
**Scope:** B-29 Terms-of-Service branch diff (uncommitted working tree) — magic-link auth data flow. Trust boundaries, fail-open/fail-closed, injection, data exposure, auth-flow integrity only. Correctness/convention/scope are the branch reviewer's `review.md` (parallel) — not re-reported here.
**Type:** Findings report only — no code changes made.

**Overall:** The version-in-the-audit-trail seam is tight: the accepted version is validated server-side against a single authority before any user lookup, carried on the server-issued token (never re-supplied by the client at consume), bound to the server-resolved `UserId`, and length-capped at the column. No injection, no enumeration regression, no secret/PII leakage, and the public legal pages are static placeholder content. The one real weakness is a **fail-closed ordering bug**: the best-effort consent write sits uncaught between the single-use link burn and JWT issuance, so a DB fault or unique-index collision there aborts an otherwise-valid sign-in *after* the link is already spent — the exact opposite of the "must never regress sign-in" design contract. Self-healing on retry, so High-availability nuisance rather than Critical.

## What's already done right
- **Version is validated server-side, fail-safe against forgery/staleness.** `RequestMagicLinkCommandValidator:18-20` enforces `NotEmpty().Equal(TermsPolicy.CurrentTermsVersion)`; the `ValidationBehavior` pipeline (`ValidationBehavior.cs:26-32`) throws before the handler runs, so a forged/stale/junk version can never reach the token or the audit record. A bad version is a clean 400 with a generic error dictionary (no leak).
- **No user-enumeration via the new field.** Validation (incl. the version `.Equal`) runs *before* `throttle.TryRegisterSend` and any user lookup in `RequestMagicLinkCommandHandler:27`, and the throttle decision ignores account existence. The 400 is identical whether or not the email maps to an account. No differential response introduced.
- **Accepted version is never client-trusted at consume.** `ConsumeMagicLinkCommand.cs` carries only `Token`; the version comes solely from the burned `MagicLinkToken.AcceptedTermsVersion` (`ConsumeMagicLinkCommandHandler:42`). No client-supplied version at consume time.
- **No IDOR on the consent write.** `UserId = user.Id` (`:48`) is the server-resolved/created user from the burned token — never anything from the request body.
- **Single-use link still burned before token issuance** (`:29-30`), and prior active links superseded per request via `InvalidateActiveForEmailAsync` (`ExecuteUpdateAsync`, set-based). Magic-link posture otherwise unchanged; token stored as hash only.
- **No injection surface.** `TermsVersion` is constrained to a constant match and `HasMaxLength(32)` at both the token column and the `TermsAcceptances` column (`TidansuDbContext.cs:34,42`); all access is parameterized EF (`AnyAsync`). Legal content is static Vue markup — no `v-html`, no markdown renderer, no user input in the render path (verified across `components/legal/*` and `views/legal/*`).
- **Public legal routes expose nothing.** `/legal/terms` and `/legal/privacy` are `requiresAuth:false`, PLAIN layout, no data fetch/session read; all operator facts are clearly-marked `[TODO]` placeholders (KRS/NIP/REGON/address/contact) — no real PII or secrets baked into the bundle.
- **Race is caught at the DB.** Unique index `(UserId, TermsVersion)` (`TidansuDbContext.cs:44`) backs `ExistsAsync` and atomically prevents duplicate/corrupt consent rows even under a check-then-insert race. `DbUpdateException` is mapped to a generic 500 with no key value leaked (`ErrorHandlingMiddleware.cs:184-209`).

## Security findings

### High
**S-H1 — Consent write is fail-closed: a DB fault (or unique-index race) between the link burn and JWT issuance aborts an otherwise-valid sign-in.**
`ConsumeMagicLinkCommandHandler.cs:42-53`. The tech-tasks contract is explicit — "Do not throw if the version is null/unknown … the flow must never regress the existing magic-link sign-in" and "Sign-in never depends on the acceptance write succeeding." The implementation honors this **only for the null case**. The write itself (`AddAsync`/`SaveChangesAsync`, `:45-52`) is **not wrapped**, and it runs *after* the single-use token is already burned (`:29-30`) and *before* tokens are issued (`:55`). Any exception in that block propagates: a transient DB error, a connection blip during the acceptance insert, or the unique-constraint collision that `TidansuDbContext.cs:43` itself anticipates ("unique-constraint catch beats a check-then-insert TOCTOU") surfaces as a 500 (`ErrorHandlingMiddleware.cs:184`/`211`) — and the user's valid magic link is already consumed. So a best-effort *audit* write can deny a legitimate sign-in and spend the link. **Reachability:** a DB fault window (any transient persistence error during the terms insert) is the realistic trigger; the pure race is hard to hit (single-use tokens + `InvalidateActiveForEmailAsync` leave one active token per email, and the token burn at `:29-30` has no optimistic-concurrency guard, so a genuine double-consume is needed). **Moderating factor:** it is self-healing — the user simply requests a fresh link, and if it was the race the now-committed row makes `ExistsAsync` return true so the block is skipped next time. Nuisance/availability, not data exposure or auth bypass. **Fix:** make the consent write truly best-effort and isolated from the auth path — wrap `:42-53` in `try/catch` that logs and continues (never rethrows), and/or move it to *after* `GenerateTokensAsync`/refresh-token persistence so a consent-write failure can never block issuing the session. Treat a `DbUpdateException` from the unique index as "already recorded" (idempotent success), not an error.

### Medium
**S-M1 — Cascade-delete FK destroys the consent audit trail — the one record you would want to retain after account deletion.**
`TidansuDbContext.cs:38-42` / migration `20260811161442_AddTermsAcceptance.cs:33-38` (`OnDelete: Cascade`). The feature's stated purpose is a *durable, historical* record of who agreed, to which version, when — legal evidence of consent. Cascade means that if/when a user row is ever deleted, every proof-of-consent row for that user is silently erased along with it. Under GDPR, proof-of-consent is typically retained as the legal basis for prior processing even after an erasure request, so cascade is the wrong default for exactly this table. **Reachability:** latent — no user-deletion path exists in the codebase today (grep found none in Application/Infrastructure/API), so there is no live data-loss now; the risk lands the moment an account-deletion or GDPR-erasure feature ships. The design note ("the consent record dies with the account") made this choice deliberately, so this is a flag for reconsideration, not an implementation slip. **Fix:** before any deletion path ships, decide the retention rule explicitly — e.g. `DeleteBehavior.Restrict`/`NoAction` (or a nullable-`UserId` `SetNull` + retained email/version/timestamp, or a soft-delete/anonymization step) so consent evidence survives account deletion. Capture the decision in the task/ADR so it isn't lost.

### Low / Hardening
**S-L1 — Token burn has no optimistic-concurrency guard; B-29's unique index newly turns a benign double-consume into a 500.**
`ConsumeMagicLinkCommandHandler.cs:22-30`. The `IsActive` check → `ConsumedAt` set → `SaveChanges` sequence is not atomic and has no rowversion, so two concurrent consumes of the same active token can both pass the burn. Pre-existing and out of B-29's scope, but worth noting because B-29's `(UserId, TermsVersion)` unique index means the loser of that race now hits `DbUpdateException` instead of silently issuing a second session. Folds into the S-H1 fix (idempotent handling of the terms write); a longer-term hardening is an optimistic-concurrency token or a conditional `ExecuteUpdate` burn so only one consume wins.

**S-L2 — `acceptedTermsVersion` is optional in the frontend client signature.**
`composables/useAuth.ts` (`acceptedTermsVersion?`) and the regenerated Kiota model. A caller omitting it sends `undefined`. Not a vulnerability — the server rejects null/empty with a 400 (`RequestMagicLinkCommandValidator:18-20`), which is the correct trust boundary (server-authoritative). Noted only so the optional client type isn't mistaken for an optional server contract; no action required.

## Verification checklist
- [ ] **S-H1 (fail-open):** With a valid outstanding magic link, simulate a failure of the `TermsAcceptances` insert (e.g. temporarily point the table at a broken constraint, or force a `DbUpdateException`) and confirm the user still receives a valid session — sign-in must NOT 500 and the link must not be wasted on the audit-write failure.
- [ ] **S-H1 (race → idempotent):** Fire two concurrent `ConsumeMagicLink` for the same new user/version and confirm exactly one `TermsAcceptances` row and at least one successful sign-in, with no unhandled 500 attributable to the unique index.
- [ ] **S-H1 (dedupe, happy path):** Re-sign-in an existing user twice with the current version → still exactly one acceptance row (earliest `AcceptedAt` preserved), no error.
- [ ] **S-M1 (retention):** Before shipping any account-deletion/erasure feature, confirm the chosen behavior retains (or intentionally anonymizes) consent evidence rather than cascade-deleting it.
- [ ] **Enumeration (regression):** POST magic-link with a bad/missing `acceptedTermsVersion` for both a known and an unknown email → identical 400, identical body, no email sent, throttle unaffected.
- [ ] **Version tamper:** POST with a stale/forged version string → 400, no token issued, no `TermsAcceptances` row, no leak of whether the account exists.
